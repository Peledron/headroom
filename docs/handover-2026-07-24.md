## Thread 2: poor write:read ratio (OPEN, root cause narrowed to one function)

The user's aggregate opus read:write is ~5.8; work sessions run 50x to 1000x. Traced
using the replay corpus `~/.headroom/replay/replay-0000.jsonl` (JSONL, each record has
`request`, `response_usage`, `transforms_applied`; segment by
`json.loads(request.metadata.user_id).session_id`). This session is `7a761a0e-cee`.

Measured facts (do not re-derive):
- This session segmented: 459 requests, write 5.5M, read 61.8M, ratio **11.2**.
- Most turns are warm and fine: write 0.5-3.5k, read 113-155k, i.e. 30-200x.
- A minority of turns bust hard: writes of 34k-99k, each re-writing OLD prefix content
  (divergence at message index 64, 141, 166, 167 of ~150-176), NOT new content.

Ruled OUT (each disproven, do not revisit):
- Token mode: this session runs hybrid (stats + init-user manifest confirm).
- Context size: read:write ratio is dimensionless; size only scales absolute tokens.
  Current context ~146k, not "big". Dropped this explanation.
- Re-masking: `MASKING_GATE` declines every turn with NEGATIVE gain (-98k..-163k) in
  `~/.headroom/logs/proxy.log`. The masking cost/benefit gate works correctly.

Ruled IN (log-proven): the `STRUCTURAL-BUST` path.
- proxy.log shows, every few turns:
  `STRUCTURAL-CHURN: client prefix diverged, alive_fraction=0.33` then
  `STRUCTURAL-BUST: alive_fraction=0.33 forcing fresh 5m write`.
- Source: `headroom/cache/prefix_tracker.py:635 observe_client_churn`. It compares this
  turn's RAW client messages to last turn's (`_last_original_messages`) via
  `_canonicalize_for_prefix_compare`, client-bytes vs client-bytes (headroom's own
  transforms excluded by design). Returns `k/n` where k = first divergent message index.
  `alive_fraction=0.33` means the client's canonicalized prefix diverges at ~1/3 depth,
  so ~2/3 of the cache is already dead and headroom writes fresh. Given that input,
  forcing the write is correct; the bug is upstream of it.
- The `0.33` is near-constant across turns, which is systematic, not organic churn.
  (Note: `survival_p_alive`=0.99 seen in the masking log is a TEMPORAL metric, unrelated
  to the structural fraction; not a contradiction.)

Two candidate root causes for the constant-0.33 client divergence (NOT yet decided):
1. Canonicalizer gap: `_canonicalize_for_prefix_compare` fails to strip something the
   client legitimately varies each turn (moved `cache_control` marker, ephemeral field,
   key ordering), so identical content miscompares as divergence.
2. Stale baseline: `_last_original_messages` not refreshed every request (docstring
   requires calling `update_from_response` once per request); comparison runs against an
   N-turn-old prefix and diverges at a fixed relative depth every time.

DECISIVE next step (proposed, not yet done): instrument `observe_client_churn` to log the
canonicalized `prev[k]` vs `current[k]` at the divergence index k. One turn of that log
says whether it is a canonicalizer gap or a stale baseline. Then the fix is a one-liner in
either the canonicalizer or the baseline update. The user approved this direction.

## Environment gotcha
Scratchpad tmpfs has a tight per-user quota. Do NOT redirect full pytest output or big
greps to files there; it makes `rtk` SIGABRT and every shell command fail. Recover with
`/usr/bin/env /usr/bin/rm -f <bigfile>`. See memory scratchpad-tmpfs-quota-breaks-rtk.
